# API worker failure, 2026-11-03 (KST)

## Findings and recovery

- Public HTTPS connected successfully, then received no HTTP response within
  18 seconds. The same symptom occurred through loopback HTTPS on the server.
- The host, nginx, MySQL, and Redis were running. Root disk use was 11%, and
  memory availability was approximately 12 GiB. No OOM event explained the fault.
- Gunicorn master PID 1870085 had run since October 17. Its workers repeatedly
  exited with raw wait status 139 (SIGSEGV with the core-dump flag). The kernel
  reported faults in Python 3.12 at instruction pointer `0x5d7455`.
- `Restart=on-failure` could not help while that master remained alive. A worker
  reload (HUP) continued to fork crashing workers from the same master.
- A separate fresh Gunicorn master using the same application and virtualenv
  successfully served HTTP requests. Django's checks also passed.
- Replacing the failing master through the existing systemd restart policy at
  23:41:10 restored the service. The three new workers remained stable. Public
  privacy-page requests returned 200 in about 0.04 seconds, unauthenticated API
  requests returned their expected 403, and `SELECT 1` succeeded for all three
  database aliases.

The immediate failure mechanism is confirmed. The initial event that corrupted
the old master's fork state or caused the native Python fault is not proven.
Neither an application-code bug nor a specific Python/library defect can be
claimed from these logs alone. Fault tracebacks are now enabled before fork to
improve the evidence available if the failure returns.

## Comparison with previous errors

- November 1 at 17:54:51: nginx logged an upstream connection closing early for
  `/toto/privacy-policy/`. The same time window contains repeated status-139
  worker failures under **the same master PID 1870085**, and the kernel reports
  the **same Python instruction pointer `0x5d7455`**. This is strong evidence of
  the same continuing native-worker failure mechanism.
- Retained application logs already contain these worker failures on October 27
  at 13:32:46. This is an earliest retained observation, not a proven start time.
  Successful API requests continued on later days, consistent with partial
  degradation before all serving workers were lost.
- October 17: nginx recorded 245 missing-backend-socket errors, including a
  prolonged interval from approximately 13:34 to 17:29. This is a different
  observed failure state. Detailed application logs from then are no longer
  retained, so the initial cause cannot be equated with the November fault.
- The user's earlier symptom (the TOTO app opened, but API operations failed)
  alone cannot identify which dated event they experienced.

## Controls added

Actual HTTP liveness, database readiness, local verified HTTPS, and worker crash
rate are checked independently. A repeated worker crash or two consecutive
liveness failures triggers replacement of the main process, with startup grace,
PID identity checks, cooldown, and a restart budget. Gunicorn fault tracebacks
and staggered worker recycling are configured. Installation, failure-mode tests,
limits, and the optional privileged nginx/systemd protection are documented in
`../README.md`.

## Other observed dependency issue

`upload.heeyun.co.kr` did not resolve during this investigation, and its Certbot
renewals failed. That is separate from TOTO's worker failure. The certificate
served for `www.heeyun.co.kr` was valid for approximately 36.7 more days. Fixing
the upload-domain DNS or retiring that unused certificate requires confirming
the intended use of that separate hostname; it was not silently removed.
